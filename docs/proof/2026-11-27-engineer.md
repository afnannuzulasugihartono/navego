## The task

A person is already signed into Chrome. The driver must reuse that authorised
session to collect an existing document and leave **one checked file** on disk:
find a named document in Google Drive My Drive, open it, download it, and record
it as a delivery whose kind and page count were read from the bytes.

Page named in the proof: `https://drive.google.com/drive/my-drive`.
Target: an existing 565 KB PDF whose name is a stable UUID
(`05b9401d-40e8-4534-af82-a0fc71382ae7.pdf`), so no private document title is
published here. Nothing was uploaded, no document was changed, and no login,
CAPTCHA or 2FA was solved.

## How the runs were driven

A Node stdio client spoke MCP to the product's own server (`navego local`),
calling the same tools an agent calls: `delivery_plan`, `browser_open_url`,
`browser_check_gate`, `browser_read_page`, `browser_find_element`,
`browser_scroll`, `browser_click`, `browser_wait_until`, `browser_download_file`.
The client waited for the extension to open a fresh browser session before the
five runs, then recorded a timestamp before each run and every tool outcome.
Raw records: `C:\Users\ASUS\Downloads\navego-eval-runs-naive.json` (five runs of
the first procedure) and `navego-eval-runs-2.json` (five runs of the corrected
procedure). Run 1 of the first set is the one that found the virtualised-grid
failure and is reported under "failure modes" below.

## Failure modes, named and fixed

1. **A false "settled".** `browser_wait_until` stamped `settled: true`
   unconditionally. Run 1's read returned 346 characters with `settled: true`
   while the file grid was still loading, and run 4 reported settled on a page
   whose `readyState` was still `loading`. An agent that trusts the word settles
   for "My Drive is empty" or clicks a rectangle from a stale read. Fixed in
   `local/browser-actions.ts`: each wait derives `settled` from its own `found`
   or `still` verdict, and `local/burst.ts` claims settled only from a step that
   found its condition. Decisions register: `local-wait-verdict-01`.
2. **A wrong file accepted as a checked delivery.** Run 1 saved a ZIP under a
   `.pdf` name; the download answered `downloaded: true` and `kind: null`, and
   `delivery_record` recorded `kind: zip` instead of refusing. Fixed in
   `local/statements.ts`: a `.pdf` whose bytes do not sniff as PDF is refused,
   naming the sniffed kind and writing no manifest line. Decisions register:
   `local-delivery-bytes-01`.
3. **A shared session allowance** (not fixed here; it is a plan and concurrency
   boundary, not a browser primitive). Two runs died with `the session
   allowance of 31 commands for plan.usd-17 is spent; reconnect to start a new
   session`. The refusal does not say that other clients on the same browser
   share the allowance, so an agent retries into the same refusal.

The claim matrix with its dated sources is `docs/api.md` -> "Honest comparison,

What each of the two needs for the same task, read on 2026-11-27:

- **Browser Use** can drive a local Chrome, but its README requires enabling
  remote debugging on `chrome://inspect/#remote-debugging`, and a named profile
  is a temporary copy rather than the live one (not on Windows). It publishes
  reliability evidence - BU Bench v2, a 60-task subset, with a per-run judge -
  that Navego does not have.
- **Skyvern** runs as a managed cloud browser or as self-hosted Docker, with
  SDKs and MCP. It claims portal work behind login, 2FA and CAPTCHA, with
  document parsing and routing.

Where Navego wins: the session boundary. No debugging port, no copied profile,
no hosted browser holding the person's cookies, and a file checked on its bytes
before it is filed as a document.

Where Navego loses, plainly: no model in the loop - the caller supplies the
steps - no CAPTCHA or 2FA automation, no general benchmark (one domain, one
task, five runs), and two of those five runs were lost to another client
spending the shared session allowance. No claim of overall superiority is
made.

## The defect and its cause

`local/doctor.ts` read both the cloud-login state and the paired-device file, but
when the bridge reported any `meterRefusal` it pushed one unconditional problem:
`the meter refused the session; update the extension to the current release and reload it`.
A fresh machine therefore got a stale-extension instruction even though the meter
had refused it because the account was not signed in and the browser was not paired.
The cause was the verdict branch, not the meter response: it discarded two facts
the doctor had already read.

## The runtime change

The doctor now derives only the setup steps that are missing. A meter refusal with
no cloud login or no device file says `sign in with \`navego auth\`, then pair the
browser`; it never blames the extension. A signed-in, paired machine still receives
the existing stale-extension advice. The rule is recorded as
`docs/decisions.json -> local-doctor-verdict-01`.

The landing page now states the same condition instead of promising `ready` on a
fresh machine: after signing in and pairing, doctor reports the plan and allowance;
before that, the machine is degraded. The install command and the five-run proof
remain on the first screen.

## The tests failed before the change

`docs/proof/2026-11-27-doctor-verdict.test.ts` and the two new assertions in
`tests/site/hero-cta.test.ts` were written first. The doctor test failed because
the unauthenticated, unpaired verdict contained `update the extension` and did not
contain `pair the browser`. The site test failed because the old unconditional
`ready` sentence did not contain the conditional wording. After the runtime and
copy changes, the two files report 9 passing tests.
