# Postmortem: dispatcher starvation, duplicate senders, and a deleted send body

Date: 2026-11-27, Asia/Jakarta. Blameless: the people and agents involved acted with the information they had. The defects were in the system and its handoffs.

##Trigger

Three separate failures on the same day:

1. Engineer product ticket 1105 had no started marker for hours; the dispatcher kept selecting a sales ticket forbidden until 2026-11-28.
2. Four Statement Harbor send automations were active at midnight, two of which could send a public message.
3. The body file for the remaining send automation was missing when checked at 22:25 WIB.

## Impact

No customer-visible outage. Product work was delayed for several hours; a duplicate public message was possible; the 00:01 send could have failed or been improvised. Settled revenue stayed $0.00, so no money was lost.

## Root causes

- A ticket whose action is time-blocked was treated as ready work because the dispatcher only read `class` and stamp, not a `not-before` date.
- A detached launcher process for a finished session kept the engineer lane marked busy; `liveSessionFor` treated `succeeded` as live.
- Duplicate automations were created across several sessions with no single register check before creating another.
- A durable automation input was stored in the approved scratch directory; a disk cleanup removed it. The cleanup itself was legitimate; the placement was wrong.

## Actions already taken

- Dispatcher parses `not-before` and `superseded-by`, frees a lane on any terminal session outcome, and orders `money -> product -> measurement`. Four tests pin this.
- Three duplicate send automations paused; one remains active, now reading its body from a repo path.
- The send body restored to `docs/proof/outreach/drafts/2026-11-28-statement-harbor.md`; automation id `aut_21da41d0e00169pXbvWR0WLUYL` points there.
- The agents area now documents triggers and contracts so a future session reads one place before creating automation.

## Prevention

- Any artefact an automation will read later must live in the repo, not in temp.
- Check `automation.list` before creating a public-action automation.
- A terminal session outcome is the liveness ground truth, not a process line.
