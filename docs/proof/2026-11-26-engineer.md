### What the lane shipped

The lane entry points had not caught up with the verifier. The verifier in
pull request #461 reads the changed paths from the diff it is given and refuses
a caller-supplied path list, because a caller that lists paths itself could
list only the paths it may touch. The generated `.opencode/agents/*.md` and
`.claude/agents/*.md` files told no lane to run the gate at all, and the ceo
lane's in-flight generator line named the old command shape, which that
verifier refuses with exit 2.

This lane renders the command the verifier accepts into every agent file, with
that role's own id and the base ref the lane's pull request targets, and adds a
role-gate test that proves the line is in both harnesses:

```
Before the merge, the scope gate: run npm run scope:role -- engineer --base <the base ref your pull request targets> --head HEAD in this worktree (a pull request against main uses origin/main); the verifier reads every changed path from that diff itself, and a non-zero exit blocks the merge.
```

The first version of that line pinned `origin/main`, and the reviewer agent
found it: on a stacked pull request that base carries the other lane's
changes, so the gate refused paths the lane never touched and the command
could not pass on the branch that published it. The command now names the base
ref the pull request targets, and the role gate pins that shape instead of one
ref.

The dispatcher lane carries the same command in the lane prompt it hands each
worker (`npm run scope:role -- <lane> --base origin/main --head HEAD`), which
is right for a lane branched from main, so the lane session and the dispatcher
run the same gate over the same diff.
