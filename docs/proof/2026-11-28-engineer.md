## What the shipped rule still gets wrong

The ticket's first bullet asks for liveness from the session's own heartbeat (`time.updated`)
**and** the absence of a running process, not from `outcome` alone. The shipped rule uses
the heartbeat, but it still lets the stored `outcome` decide the idle case: a session that
never ran a turn is a target at any age, and a session that finished its last run stops
being a target thirty minutes later, even while the OpenCode service that owns it is
running and the context is still resumable.

Measured with the shipped resolver and the live session record:

```text
live record: {"id":"ses_df1a6877cffen04QvCBE2T0ysR","title":"slot-console/agent-manager-20261126","outcome":"succeeded","ageMinutes":16}
resolved at the live heartbeat: ses_df1a6877cffen04QvCBE2T0ysR
same session, 40 minutes after its last run: null
same session, 40 minutes old, but never ran a turn: ses_df1a6877cffen04QvCBE2T0ysR
```

Why that matters: the operator console session runs about once an hour. Its heartbeat is
therefore older than the thirty-minute stale window for roughly half of every hour, and in
that half every report to the operator fails with `TARGET_SESSION_MISSING` again - the same
refusal the ticket was written about. The fix belongs to the lane that owns the file; the
process table the watchdog already reads (`readEvidence()` in `scripts/dev/agent-fleet/watch.ts`)
is the second signal the ticket named, and `sendMessage` does not carry it today.
